## Вариант 4

Исследуются три модели из первой лабораторной работы.

| Модель | Расчёт следующего состояния |
| --- | --- |
| 1.4 | `y[k+1] = a y[k] + b (u[k] − u[k−1])` |
| 2.6 | `y[k+1] = a₁ y[k]³ − a₂ y[k−1] + b u[k]²` |
| 3.8 | `y[k+1] = y[k] + Δt (−a₁ y[k] − a₂ y[k]² + b u[k])`, явный метод Эйлера |

В начале каждого опыта симулятор задаёт `y[−1] = y[0] = y₀` и `u[−1] = 0`. Строка CSV с индексом k содержит состояние до применения входа u[k]. Поэтому при n шагах получается n + 1 строка данных. Если очередное значение выходит за предел 10⁶ по модулю или становится неконечным, симулятор завершает опыт на последней допустимой строке.

## Устойчивость модели 1.4

При нулевом входе получаем `y[k+1] = a y[k]`. Подстановка решения вида `zᵏ` даёт характеристическое уравнение `z − a = 0` с единственным корнем `z = a`. Свободный отклик равен `aᵏ y₀`. Коэффициент b влияет на вынужденный отклик.

| Положение корня | Поведение при ненулевом начальном состоянии |
| --- | --- |
| `abs(a) < 1` | Отклик стремится к нулю. Система асимптотически устойчива. |
| `a = 1` или `a = −1` | Модуль отклика постоянен. При −1 знак чередуется. |
| `abs(a) > 1` | Модуль отклика растёт. |

Программа сообщает о корне на границе или за её пределами до вывода таблицы. Проверка фактического расхождения действует во время расчёта для всех трёх моделей.

## Речь для защиты на три минуты

В первой лабораторной у меня была программа с тремя математическими моделями. Она принимала числа, выполняла расчёт и сохраняла таблицу. Представьте, что программист исправил одну строку. Проект по-прежнему собирается, таблица открывается, график выглядит правдоподобно. Как коллеге понять, можно ли выпускать эту версию? Во второй работе я сделал так, чтобы ответ можно было получить за один запуск.

Покажу на модели 1.4. Для неё важно, насколько вход изменился с прошлого шага. Возьмём начальное состояние 1, коэффициенты 0,5 и 2. Сначала подадим на вход единицу, потом ноль. Ответы легко проверить вручную. На первом шаге берём половину единицы и прибавляем двойку, получается 2,5. На втором берём половину от 2,5 — это 1,25. Вход упал с единицы до нуля, поэтому вычитаем двойку. Получаем минус 0,75. Оба ответа я записал в тест.

Теперь представим обычную ошибку при правке. Программист убрал из формулы предыдущий вход. На первом шаге тест по-прежнему увидит 2,5, ведь в начале предыдущий вход равен нулю. А на втором шаге программа пропустит вычитание и вернёт 1,25. В выводе теста видно и ожидаемое число, и фактическое. Разработчик сразу получает короткий воспроизводимый пример и знает, где искать ошибку. Ему не нужно просматривать всю таблицу или просить коллегу повторить вычисления.

Есть и другая причина неожиданного результата — сами настройки. Отключим влияние входа и начнём с восьми. При коэффициенте минус половина получим восемь, минус четыре, два, минус один. Отклонение затухает. При минус единице размах сохраняется, а при минус двух растёт. Программа различает эти случаи ещё до расчёта. Так пользователь может понять, почему при исправном коде он получает растущие значения.

В конце я запускаю 27 модульных тестов и отдельную сквозную проверку. Она подаёт данные в настоящую программу и проверяет созданные CSV, поэтому помогает поймать ошибку даже при правильной формуле — например, если результат записался под чужим именем. Затем отчёт показывает, какие строки выполнялись. В измеренном запуске это 292 из 306 строк.

Для команды выгода конкретная. Однажды проверенный вручную пример становится постоянной проверкой. После следующей правки один разработчик может сам повторить весь набор, увидеть точное расхождение и проверить исправление. Время коллеги остаётся на новые случаи, которые ещё никто не проверял.
